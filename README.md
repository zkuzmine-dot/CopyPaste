# CopyPaste

Сервис для обмена текстом и файлами между устройствами (FastAPI + PostgreSQL).

Два режима:

- **Заметки** — сохранить текст и до 10 файлов, поделиться ссылкой или QR-кодом. Можно задать
  срок хранения, удалить заметку после первого прочтения или закрыть паролем — тогда текст и
  файлы хранятся зашифрованными.
- **Каналы** — буфер обмена между двумя устройствами в реальном времени. Одно устройство
  создаёт канал, второе подключается по QR-коду, ссылке или 8-символьному коду. Отправитель
  пишет текст или кидает файлы, получатель видит ленту: у текста кнопка «Скопировать», у файла —
  превью и «Скачать». Роли можно поменять.

Файлы прикрепляются кнопкой, перетаскиванием или вставкой из буфера (Ctrl+V), с полоской
прогресса.

## Запуск

```bash
cp .env.example .env   # заполнить своими значениями
make up
```

`FILES_SIGNING_SECRET` в `.env` обязателен (не короче 32 символов), без него приложение не
стартует. Сгенерировать:

```bash
python -c "import secrets; print(secrets.token_urlsafe(32))"
```

- приложение: http://localhost:8000
- документация API: http://localhost:8000/docs

Канал шифрует сообщения в браузере, а WebCrypto работает только на HTTPS или `localhost`.
Поэтому по адресу вида `http://192.168.x.x:8000` заметки с телефона открываются, а канал —
нет. Для канала на телефоне нужен HTTPS, например туннель до `localhost:8000`; его адрес и
попадёт в QR-код.

## Устройство

Контейнеры:

- `db` — PostgreSQL 16;
- `redis` — Redis 7 без сохранения на диск: попытки ввода паролей, ключи файлов на время после
  ввода пароля, лимит загрузок;
- `app` — FastAPI под uvicorn: страницы, REST API и WebSocket;
- `scheduler` — APScheduler (`AsyncIOScheduler`): чистка заметок и каналов, сборщик файлов,
  сверка диска с БД.

Байты файлов лежат в именованном томе `filedata` (`/data/files`), общем для `app` и
`scheduler`. Не в папке проекта: она смонтирована в контейнер и попала бы в git.

```
app/
  api/notes/, api/channels/,  HTTP- и WebSocket-ручки — только разбор запроса и ответ
  api/files/
  services/                   бизнес-логика; flush, но не commit
  db/                         модели SQLAlchemy и подключение
  storage/                    где лежат байты файлов: интерфейс и реализация на диске
  realtime/                   кто к каким каналам подключён, ограничение частоты
  security/                   то, что в Redis: попытки паролей, ключи файлов, лимит загрузок
  schemas/                    Pydantic-схемы, в том числе событий WebSocket
  utils/                      шифрование, подписанные ссылки, Range, тип файла, QR, токены
  jobs/, scheduler.py         периодическая чистка
  static/                     фронтенд без сборки: index.html, app.js, channel.js, files.js,
                              channel-crypto.js (ключи канала), channel-keystore.js (IndexedDB)
  static/fonts/               IBM Plex Sans и Mono (SIL OFL 1.1, тексты лицензий рядом)
```

## Асинхронность

Приложение асинхронное целиком: ручки, WebSocket и задачи планировщика работают в одном цикле
событий. PostgreSQL — через `AsyncSession` и psycopg 3 (тот же `DATABASE_URL`), Redis — через
`redis.asyncio`, миграции Alembic — через асинхронный движок.

### Транзакции

- HTTP-ручки получают сессию из зависимости `DbSession` (`get_db`). Коммит — после ручки, но до
  отправки ответа (`scope="function"`), при ошибке — откат.
- WebSocket, загрузка и скачивание файлов — короткая транзакция на каждый шаг:
  `run_db(factory, fn)`. Медленная передача не держит соединение с БД.
- Задачи планировщика — `async with session_factory() as db, db.begin()`.

### Ничего не догружается само

Обращение к незагруженной связи или протухшему атрибуту — это скрытый запрос. В async он
невозможен и падает с `MissingGreenlet`, поэтому всё, что нужно, загружается явно:

- `expire_on_commit=False` — после коммита объекты не протухают;
- у связи `Participant.channel` — `lazy="raise"`, канал запрашивают через `joinedload`;
- после `UPDATE` объект перечитывается через `refresh()`, значения, которые считает сама БД, —
  через `RETURNING`.

В тестах скрытая догрузка — ошибка `ImplicitLoadError` с текстом запроса, а не
`MissingGreenlet` где-то в глубине SQLAlchemy.

### Что работает в потоках и почему

Цикл событий один: пока он занят, ждут все запросы и все каналы. Поэтому то, что держит
процессор или ждёт локальный диск, уходит в поток, а БД, Redis и WebSocket потоков не занимают.

| Что | Почему | Как |
|---|---|---|
| Argon2 — создание и открытие заметки с паролем | ~0,1 с процессора на попытку | `crypto.in_kdf_thread`, не больше `KDF_MAX_CONCURRENT` одновременно |
| шифрование файлов заметки, расшифровка при скачивании | процессор и диск | `run_in_threadpool`; тело ответа Starlette читает в потоке |
| запись загрузки, чтение и удаление файлов | у локального диска нет неблокирующего API | `anyio.Path`, `run_in_threadpool`, `anyio.to_thread` |
| QR-код | процессор | `run_in_threadpool` |
| сверка диска с БД в `scheduler` | обход всех файлов | `anyio.to_thread`, пачками |

- Создание заметки с паролем и файлами защищено от отмены (`CancelScope(shield=True)`): клиент,
  оборвавший запрос между коммитом и уборкой, иначе оставил бы на диске открытый исходник.
- Пул Redis — с ожиданием (`BlockingConnectionPool`): при всплеске запросов команда ждёт
  свободное соединение до 1 с, а не получает ошибку. Обычный пул отказывал бы сразу, и пароли
  отвечали бы 503, а загрузки уходили бы на запасной лимит в памяти.

## API заметок

| Метод и путь | Что делает |
|---|---|
| `POST /api/notes` | создать заметку; `file_ids` — до 10 id из `POST /api/files`, текст тогда можно не присылать |
| `GET /api/notes/{slug}` | получить заметку со ссылками на файлы (одноразовую — без текста и без ссылок) |
| `POST /api/notes/{slug}/read` | прочитать; одноразовая заметка удаляется, её файлы получают одноразовые ссылки |
| `PUT /api/notes/{slug}` | изменить текст или срок хранения (файлы не меняются) |
| `DELETE /api/notes/{slug}` | удалить |
| `POST /api/notes/{slug}/unlock` | открыть заметку с паролем: `{"password": "..."}` → текст и ссылки на файлы |
| `POST /api/notes/{slug}/delete` | удалить заметку с паролем, пароль — в теле |
| `GET /api/notes/{slug}/qr` | QR-код со ссылкой (SVG) |

У заметки с паролем `GET` отдаёт `has_password: true`, срок и имена файлов, но без текста и без
ссылок, а `read`, `PUT` и `DELETE` отвечают 409. Пароль передаётся только в теле запроса: адреса
попадают в логи.

## Заметки с паролем

Пароль задают при создании (`password`, 4–128 символов). Восстановить забытый пароль нельзя,
сменить или снять — тоже. Изменить такую заметку нельзя, удалить — только с паролем.
Одноразовая заметка с паролем сгорает после верного пароля; неверный её не трогает.

### Шифрование

```
пароль --NFC--> Argon2id(соль, t, m, p) --> KEK (32 байта, нигде не хранится)
                                             |
DEK (32 случайных байта) ---AES-GCM(KEK)---> wrapped_key                 в БД
  |
  +---AES-GCM---> ciphertext                                             в БД, text = ''
  +---AES-GCM кусками по 64 КиБ---> байты файлов                         на диске
```

- **Конвертная схема.** Пароль шифрует не текст, а случайный ключ заметки (DEK). Поэтому файлы
  шифруются тем же ключом, а сменить пароль в будущем можно, перешифровав только DEK.
- **Проверка пароля — это расшифровка.** Отдельного хэша нет: неверный пароль даёт другой KEK,
  и тег AES-GCM не сходится. Хэш рядом был бы ещё одной мишенью для подбора.
- **Argon2id** с t=10, 64 МиБ, p=4 — около 0,1 с на попытку (0,35 с на одном ядре).
  Параметры хранятся в каждой заметке: их можно ужесточить, а старые заметки откроются со
  своими. Одновременно ключ вычисляют не больше `KDF_MAX_CONCURRENT` запросов, иначе подбор
  съел бы память сервера.
- **AAD** привязывает шифротекст к заметке и назначению: текст одной заметки не подложить в
  другую, а зашифрованный ключ — не выдать за текст.
- **CHECK в БД:** заметка не бывает зашифрована «наполовину», и у зашифрованной `text` пустой.

### Попытки и заморозка

Счётчики неверных паролей — в Redis, каждый обновляется одним Lua-скриптом, атомарно.

| Предел | По умолчанию | От чего защищает |
|---|---|---|
| адрес | 10 неверных за 15 минут → заморозка на 15 минут | один атакующий перебирает много заметок |
| заметка | 5 неверных за минуту → блокировка на минуту | подбор к одной заметке с многих адресов |

- Заморозка проверяется до Argon2: замороженный адрес не тратит память и CPU сервера.
- 403 — неверный пароль, в `detail.attempts_left` — сколько попыток осталось. Если эта ошибка
  включила заморозку, в ней сразу есть `Retry-After`. Дальше — 429 с `Retry-After`.
- Верный пароль сбрасывает счётчик заметки, но не адреса.
- Redis недоступен — `/unlock` и `/delete` отвечают 503: без счётчиков подбор шёл бы без
  ограничений. Остальное без Redis работает.
- 422 не возвращает введённый пароль. FastAPI по умолчанию кладёт значение в поле `input` — даже
  у `SecretStr`, — поэтому у ошибок валидации свой обработчик.
- Ответ с расшифрованным текстом — с `Cache-Control: no-store`.

### Файлы заметки с паролем

- До ввода пароля у файлов нет ссылок, только имя и размер. После — ссылки на
  `PROTECTED_FILE_URL_TTL_SECONDS`, у одноразовой заметки — одноразовые.
- Байты шифруются при создании заметки: загружается файл раньше, когда пароля ещё нет.
  Зашифрованная копия пишется под новым ключом хранилища, строка в БД переходит на неё в той же
  транзакции, а открытый исходник стирается после коммита. Откат или сбой оставляют только
  лишний файл на диске — его уберёт сверка диска с БД.
- Файл шифруется кусками по 64 КиБ, каждый со своим тегом. Nonce куска — 8 случайных байт файла
  и номер куска; в AAD — id файла, номер и признак «последний». Куски нельзя переставить,
  подложить из другого файла или отрезать хвост.
- После `/unlock` ключ заметки лежит в Redis `FILE_KEY_CACHE_SECONDS`. В ссылке только `key_id`
  этой записи, и он входит в подпись ссылки; сам ключ не попадает ни в адрес, ни в логи. Ссылка
  не живёт дольше записи: срок вышел — 403, заметку открывают паролем заново.
- Скачивание расшифровывает на лету, `Range` читает с диска только нужные куски (206, 416,
  `If-Range`). Подменённый кусок даёт ошибку, а не мусор; если это случится посреди передачи,
  соединение оборвётся раньше `Content-Length`.

## Файлы

### Загрузка

| Метод и путь | Кто может |
|---|---|
| `POST /api/files?name=...` | любой: файл для заметки |
| `POST /api/channels/{slug}/files?name=...` | отправитель канала после обмена ключами (иначе 409), токен в `X-Participant-Token` |

- Тело запроса — сами байты файла, без multipart. Сервер читает их потоком и обрывает на
  `FILE_MAX_SIZE_BYTES` + 1 байт (413), не дожидаясь конца: `Content-Length` можно не прислать
  или подделать.
- Тип определяется по первым байтам, заголовку клиента не верим. Картинками считаются только
  PNG, JPEG, GIF и WebP — у них есть превью, всё остальное `application/octet-stream`.
- Ответ: `id`, `name`, `size`, `content_type`, `is_image`. Файл ждёт привязки
  `PENDING_UPLOAD_TTL_SECONDS` (к заметке — через `file_ids`, в канал — событием `send_file`).
- 429 — слишком много загрузок с одного адреса, 507 — исчерпана квота `FILES_MAX_TOTAL_BYTES`.

### Скачивание и подтверждение

Ссылки на файлы выдаёт сервер в ответах заметок и событиях канала, их не собирают вручную:

- `download_url` — `GET /api/files/{id}?exp=...&sig=...`. Подпись HMAC-SHA256 со сроком,
  проверяется до обращения к БД. Файл всегда отдаётся как скачивание, с `nosniff` и
  `Content-Security-Policy: sandbox`, поддерживается докачка (`Range`). У файлов заметки с
  паролем в ссылке ещё `key_id` — см. «Заметки с паролем»;
- `preview_url` — то же с `inline=1`, только у картинок;
- `received_url` — только у одноразовых файлов: `POST` сюда, когда файл скачан целиком.

**Одноразовые файлы удаляются по подтверждению клиента, а не по факту отдачи.** Сервер видит
лишь, что передал байты ядру: файл в несколько мегабайт целиком уходит в буферы сокетов за
миллисекунды, даже если клиент успел получить сотни килобайт и связь оборвалась. Поэтому
страница качает такие файлы сама (`fetch`, с прогрессом), продолжает после обрыва с того же
байта и только потом шлёт `received_url`. Без подтверждения файл доживает свой срок, и его
удаляет сборщик.

### Жизненный цикл

| Файл | Сколько живёт |
|---|---|
| загружен, ни к чему не привязан | `PENDING_UPLOAD_TTL_SECONDS` |
| в заметке | сколько живёт заметка |
| в одноразовой заметке после прочтения | до подтверждения получения, но не дольше `BURN_NOTE_FILES_WINDOW_SECONDS` |
| в канале | до подтверждения получения, но не дольше `CHANNEL_FILE_TTL_SECONDS` |

У строки файла владелец (заметка или сообщение) привязан через `ON DELETE SET NULL`. Когда
владельца удаляют, файл остаётся «без владельца», и сборщик (`run_files_gc`, раз в
`FILES_GC_INTERVAL_SECONDS`) удаляет и строку, и байты. Остальной код про диск не знает.

Порядок операций: загрузка — сначала байты, потом строка в БД; удаление — сначала строка,
потом байты. Сбой между шагами оставляет только лишний файл на диске, его раз в
`FILES_DISK_SWEEP_INTERVAL_SECONDS` убирает сверка диска с БД (`run_disk_sweep`) — вместе с
недописанными загрузками.

### Хранилище и переход на MinIO

Код работает с интерфейсом `FileStorage` (`app/storage/base.py`), сейчас реализация одна —
`LocalFileStorage`: запись во временный `.part`, атомарное переименование в ключ вида
`ab/cd/<hex>`. Ключ генерирует сервер, имя от пользователя в путь не попадает.

Для MinIO/S3 нужен класс `S3FileStorage` и контейнер `minio`. Обычные файлы можно отдавать
редиректом на presigned-ссылку S3, загрузку — перевести на presigned PUT: схема «загрузить →
привязать» к этому уже готова. Сервисы, API и фронтенд при этом не меняются.

### Безопасность

- превью только у PNG/JPEG/GIF/WebP, определённых по содержимому; SVG и HTML всегда
  скачиваются и не выполняются на нашем домене;
- ссылки подписаны и ограничены по времени; ссылки на файл в канале получает только
  получатель, отправитель видит свой файл без ссылок;
- в канал можно отправить только свою загрузку и только для канала (`uploaded_by_id`, `origin`);
  привязка к заметке — одним условным `UPDATE`, так что один файл не попадёт в две заметки;
- лимиты: размер файла, частота загрузок, общая квота хранилища;
- файлы заметок с паролем лежат на диске зашифрованными.

## Каналы

### REST

| Метод и путь | Что делает |
|---|---|
| `POST /api/channels` | создать канал; создатель — получатель. Ответ: `slug`, `token`, `role` |
| `POST /api/channels/{slug}/join` | подключиться с `{"key_commitment": ...}` — отпечатком ключа устройства; 404 — канала нет, 409 — уже два участника, 422 — нет отпечатка |
| `GET /api/channels/{slug}` | состояние канала, как в событии `state`; токен в заголовке `X-Participant-Token` |
| `GET /api/channels/{slug}/qr` | QR-код со ссылкой на страницу канала (SVG) |
| `POST /api/channels/{slug}/files` | загрузить файл (только отправитель), см. «Файлы» |

Токен участника выдаётся один раз, в базе хранится только его SHA-256. Фронтенд держит токен
в `localStorage`, поэтому после перезагрузки страницы вы остаётесь тем же участником.

### WebSocket `/ws/channels/{slug}`

Все сообщения — JSON с полем `type`. Токен передаётся первым сообщением, а не в адресе:
адреса попадают в логи.

Клиент → сервер:

| Событие | Поля | Кто может |
|---|---|---|
| `auth` | `token` | первым сообщением, в течение `WS_AUTH_TIMEOUT_SECONDS` |
| `public_key` | `key` — открытый ключ устройства | один раз, в порядке из «Обмена ключами» |
| `send` | `payload` — зашифрованный текст (29–300 028 байт, см. «Шифрование текста») | только отправитель, после обмена ключами |
| `send_file` | `file_id` — id своей загрузки | только отправитель, после обмена ключами |
| `become_sender` | — | только получатель |

Сервер → клиент:

| Событие | Поля | Когда |
|---|---|---|
| `state` | `role`, `peer_joined`, `peer_online`, `messages`, `key_sent`, `peer_key_commitment`, `peer_public_key` | сразу после `auth`, всегда первым |
| `peer_joined` | `key_commitment` | второе устройство вошло в канал — создателю |
| `peer_key` | `key` | собеседник отправил свой ключ |
| `message` | `id`, `kind` (`text`/`file`), `payload` (у текста), `file`, `created_at`, `expires_at` | новое сообщение — обоим участникам; у файла ссылки только у получателя |
| `file_downloaded` | `message_id` | получатель подтвердил, что скачал файл, — обоим |
| `roles_changed` | `role` | после `become_sender` — каждому его новая роль |
| `peer_status` | `online` | второе устройство подключилось или отключилось |
| `error` | `code`, `detail` | `invalid_event`, `not_sender`, `not_receiver`, `file_not_found`, `rate_limited`, `already_authenticated`, `keys_not_ready`, `key_out_of_order`, `key_already_sent`, `key_mismatch` |
| `channel_closed` | `reason` | канал закрыт; следом соединение закрывается с кодом 4410 |

Коды закрытия:

| Код | Причина |
|---|---|
| 1009 | сообщение больше `WS_MAX_MESSAGE_BYTES` |
| 4401 | нет `auth` вовремя или токен не подходит к каналу |
| 4404 | канал не существует или уже закрыт |
| 4409 | этот участник подключился в другой вкладке — старое соединение закрыто |
| 4410 | канал закрыт по бездействию |

Одно и то же сообщение может прийти и в `state`, и отдельным событием `message` — клиент
отбрасывает повторы по `id`.

### Обмен ключами

Каждое устройство создаёт пару ключей ECDH P-256 (WebCrypto), сервер хранит только открытые
ключи и пересылает их собеседнику. Ключ — несжатая точка (65 байт), отпечаток — его SHA-256;
в JSON оба передаются в base64url без `=`. Порядок строгий:

1. Подключившийся входит (`join`) с отпечатком своего ключа, создатель получает его в
   `peer_joined` или в `state`.
2. Создатель отправляет `public_key` — только после отпечатка, иначе `key_out_of_order`.
3. Подключившийся получает `peer_key` и отправляет свой `public_key` — только после ключа
   создателя и только тот, что совпал с отпечатком (`key_mismatch`).

Каждый ключ принимается один раз (`key_already_sent`), а `send` и `send_file` до обмена
отвечают `keys_not_ready`. Порядок нужен для проверки глазами: обе стороны фиксируют ключ
раньше, чем видят чужой, поэтому сервер не может подобрать подменные ключи так, чтобы
проверочные фигуры на устройствах совпали. Если создателя нет в сети, когда подключается
второе устройство, второе ждёт: шаг 2 сделает создатель, когда вернётся.

В браузере (`static/channel-crypto.js`, `static/channel.js`):

- приватный ключ создаётся неизвлекаемым и лежит в IndexedDB вместе с ролью в обмене, поэтому
  канал переживает перезагрузку страницы. Удаляется вместе с токеном, когда канал закрыт;
- из общего секрета ECDH через HKDF-SHA-256 получаются два ключа AES-256-GCM, для текста и для
  файлов. В HKDF входят код канала и оба открытых ключа в порядке «создатель, подключившийся»;
- фигуры — первые 20 бит SHA-256 от обоих ключей: 4 фигуры по 5 бит (16 форм, залитая или
  контурная). Подмена ключа посередине угадывает их с шансом 1 к 1 048 576;
- создатель сверяет ключ собеседника с отпечатком и раскрывает свой ключ одному отпечатку за
  канал. Другой отпечаток или другой ключ собеседника после переподключения — экран «Ключи не
  сошлись», и устройство забывает канал.

### Шифрование текста

Текст шифрует браузер ключом для текста, сервер хранит и пересылает только `payload`:
12 байт случайного nonce, шифротекст и 16 байт тега AES-GCM, в JSON — base64url без `=`.
В AAD входят код канала и тип сообщения, поэтому шифротекст не перенести в другой канал и не
выдать текст за описание файла. Испорченное или чужое сообщение не расшифруется — в ленте будет
«Не удалось расшифровать сообщение».

Сервер проверяет только длину: от 29 байт (непустой текст) до 300 028 — поле ввода
ограничивает текст 100 000 знаками UTF-16, а в UTF-8 такой знак занимает не больше 3 байт.
В base64 это около 400 КБ, с запасом меньше `WS_MAX_MESSAGE_BYTES`.

Отправителя в AAD нет: лента не показывает, кто прислал сообщение, и роли меняются, так что
такая привязка ничего бы не защищала. Защиты от повтора тоже нет — сервер может прислать
старое сообщение ещё раз, подделать или изменить его не может.

### Жизненный цикл

- текст живёт `MESSAGE_TTL_SECONDS`, файл — `CHANNEL_FILE_TTL_SECONDS` или до подтверждения
  получения;
- канал закрывается, если в нём `CHANNEL_IDLE_TIMEOUT_SECONDS` ничего не отправляли и не меняли
  роли. Срок считается от `last_activity_at` в базе: таймер в `app` спит ровно до этого момента
  и закрывает канал, а если активность была — засыпает снова;
- `scheduler` раз в `CHANNEL_CLEANUP_INTERVAL_SECONDS` удаляет протухшие сообщения и
  неактивные каналы (участники и сообщения — каскадом). Это же страхует перезапуск `app`,
  при котором таймеры в памяти теряются.

Действия в канале сериализуются блокировкой строки канала (`SELECT … FOR UPDATE`): два
одновременных подключения не займут один слот, ни текст, ни файл не уйдут во время смены
ролей, второй ключ устройства не перезапишет первый, а чистка не удалит канал из-под
отправляемого сообщения. На это есть тесты в
`tests/test_channels_concurrency.py`.

## Ограничения

- **Один процесс `app`.** Список подключений к каналам и таймеры закрытия каналов хранятся в
  памяти процесса. При нескольких воркерах или репликах нужен общий брокер (например, Redis
  pub/sub). Лимит загрузок и попытки паролей уже в Redis и общие для всех процессов; пока Redis
  недоступен, лимит загрузок считается в памяти.
- **Лимиты частоты — от случайного флуда, а не от атак.** Лимит WebSocket — на соединение,
  переподключение сбрасывает счётчик. Лимит загрузок и заморозка паролей — по IP-адресу; в
  Docker Desktop все запросы приходят с адреса шлюза, поэтому локально они общие: неверные
  пароли с телефона заморозят и компьютер. За обратным прокси нужен `--proxy-headers` с
  доверенным адресом прокси; `X-Forwarded-For` от произвольного клиента не читаем — так обходили
  бы заморозку.
- **Пароль — не end-to-end.** Сервер видит текст и файлы в момент сохранения и открытия.
  Шифрование защищает от утечки дампа БД и диска, но не от взломанного сервера.
- **Короткий пароль при утечке дампа подбирается офлайн** — там лимиты Redis не работают,
  Argon2id лишь делает каждую попытку дорогой.
- **Файлы до создания заметки лежат открыто** — между загрузкой и сохранением заметки, обычно
  минуты. Полностью это закрыло бы только шифрование в браузере.
- **Ключ файлов живёт в Redis `FILE_KEY_CACHE_SECONDS`** после ввода пароля — в памяти, Redis
  запущен без сохранения на диск.
- **Подтверждение получения — на совести клиента.** До подтверждения тот, у кого есть ссылка
  (получатель или читатель одноразовой заметки), может скачать файл несколько раз — но только
  в пределах его срока.
- **Одноразовый файл скачивается в память браузера** и только потом сохраняется. Для 50 МБ это
  нормально; при лимите в сотни мегабайт понадобится запись на диск по частям.
- **Без Docker на Windows** psycopg в async-режиме не работает с циклом событий по умолчанию
  (`ProactorEventLoop`), нужен `SelectorEventLoop`. Приложение и тесты рассчитаны на запуск в
  контейнере.
- Нет антивирусной проверки и удаления EXIF из фото (в нём бывают геометки).

## Тесты

```bash
make test
make test-js
```

`make test-js` проверяет `static/channel-crypto.js` в Node тем же WebCrypto, что в браузере:
одинаковые ключи и фигуры у обоих устройств, разные — при подмене ключа, независимый пересчёт
фигур через `node:crypto`; текст, зашифрованный одним устройством, читает другое, а испорченный,
обрезанный или чужой не расшифровывается; самый длинный текст укладывается в лимит сервера.

Тесты асинхронные (pytest + anyio) и идут в одном цикле событий с приложением: HTTP и WebSocket —
через `httpx2.AsyncClient` с `ASGIWebSocketTransport`, без uvicorn и сети.

- База — отдельная `<имя базы>_test`: пересоздаётся при каждом запуске, к ней применяются
  миграции. Обычный тест — одна внешняя транзакция, которая в конце откатывается; сессии
  приложения работают внутри неё через SAVEPOINT.
- Гонки, WebSocket и одновременные запросы — на настоящих коммитах (`committing_session_factory`,
  `committing_client`): у каждой сессии своё соединение, после теста таблицы очищаются. Окно
  гонки растягивает `anyio.sleep` внутри транзакции, пока она держит блокировку.
- Redis — отдельная логическая база 15, очищается до и после каждого теста. Argon2 — с
  минимальными параметрами, файлы — во временной папке, а не в томе приложения.
- **blockbuster**: блокирующий вызов из кода `app` в цикле событий (`time.sleep`, файл,
  синхронный сокет) роняет тест с `BlockingError`. Код самих тестов и потоки блокировать могут.
- **Скрытые запросы** роняют тест с `ImplicitLoadError` (см. «Ничего не догружается само»).
- **Debug-режим asyncio** предупреждает о шагах цикла дольше 0,1 с и падает, если цикл трогают
  из чужого потока. Включается по желанию: на смонтированной папке Windows он вдвое замедляет
  тесты.

  ```bash
  docker compose exec -e ASYNCIO_DEBUG=1 app pytest
  ```

Защиты проверены «от обратного»: если убрать блокировку строки, Lua-скрипт, признак последнего
куска, `key_id` в подписи, обработчик 422, поток для Argon2, `shield` при создании заметки или
ожидание в пуле Redis, соответствующие тесты падают.

ASGI-транспорт не открывает настоящих сокетов, поэтому изменения WebSocket и передачи файлов
(обрыв, докачка) стоит дополнительно проверять вживую: две вкладки или компьютер и телефон через
`make up`.
